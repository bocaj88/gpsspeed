# 2. History: the Arduino Uno builds (v1–v3)

The first versions were an Arduino Uno with a perfboard "hat": a GPS module, a logic-level MOSFET
(IRLZ44N) pulling the signal line to ground, and a 3-way screw terminal for +12 V / GND / SIGNAL.
GPS module: a MakerFocus GT-U7 (NEO-6M compatible), <https://www.amazon.com/dp/B07P8YMVNT>.
The code is in [`legacy/arduino-uno/`](../legacy/arduino-uno/).

They worked well enough to prove the idea on the boat. They also ran into every problem the v4
board was designed around.

## v1: proof of concept

- GPS speed read with TinyGPS++, and a square wave generated by toggling a pin in `loop()`.
- **Never use `delay()`.** The pulse is scheduled by comparing `micros()` against the next toggle
  time, so reading the GPS doesn't stall the output.
- Speed could also be typed in over USB serial, which is how the first Hz-per-MPH constant was
  tuned against the dash.

## The one-serial-port problem

The Uno has one hardware UART, and the GPS and the USB serial monitor both want it.

- **GPS on SoftwareSerial:** the serial monitor works, but bit-banging the GPS at 9600 baud keeps
  interrupting the pulse loop. **Above ~21 MPH the pulses stretched and the dash jumped to ~30 MPH.**
  This was the wall that stopped the Uno approach.
- **GPS on hardware serial:** the pulses are clean at speed, but there's no serial monitor, and you
  have to unplug the GPS to upload. That's how many copies of the sketch came to exist (`v1_serial`,
  `v1_sw_serial`, …).

## v2: consolidated

- One sketch, with a compile-time switch for which serial the GPS uses.
- GPS raised from 1 Hz to **10 Hz** (UBX commands to the NEO-6M), plus a **lag predictor**. PerfectPass
  was oscillating because the speed it saw lagged the real speed.
- **Self-test mode:** holds 0/10/15/20/22/24/26/30 MPH for 30 s each, so the dash reading can be
  written down at each step and the constant fitted.
- The original "sweep the speedo while waiting for GPS lock" idea was **removed**: PerfectPass tried
  to follow the sweep. v2 pins the output to **5 MPH** until there's a fix.

## v3: Timer1

- Moves the output to **pin 9 (OC1A)** so the Uno's Timer1 hardware toggles the pin. The pulse no
  longer depends on how busy `loop()` is.
- The hat only breaks out pin 6, so v3 needs one jumper wire. It sets pin 6 to a high-impedance
  input, so leaving the old wire in place can't make two outputs fight each other.

## Why the Uno timing read ~4.42 Hz/MPH

The v1/v2 pulse code rounded every half-period **down** to a multiple of 128 µs. That made the real
output 1–2.5 % fast, increasingly so at higher speed. Tuned against the dash, the effective constant
across 15–26 MPH came out around **4.42 Hz/MPH**. The v4 board generates the frequency exactly, so
it starts from the Uno's *effective* value to read the same on the dash.

## Lessons that shaped v4

1. **Don't generate the pulse in software.** Use a hardware timer clocked from a crystal.
2. **The GPS gets its own UART**, and USB serial stays free for debugging.
3. **Power and wiring faults are real.** In this project a VCC-to-GND short killed a perfboard, a
   GPS module, and one Uno's USB chip. v4 has reverse-polarity, transient, and miswire protection.
4. **No laptop at the dock.** Settings and updates have to come from a phone.
5. **Never sweep the output.** Hold a steady value when there's no data.
